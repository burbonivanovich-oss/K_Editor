# /factcheck — проверка фактов одной статьи

Извлекает claims из статьи (даты, суммы, упоминания НПА, ссылки) и сверяет
каждый с актуальным первоисточником. Возвращает JSON-отчёт со статусами и
рекомендации по правкам.

Запускается по slug: `/factcheck 2026-01-15-chto-takoe-ts-piot`.

## Алгоритм

### Шаг 1 — Извлечь claims

```bash
node scripts/factcheck/extract-claims.mjs <slug>
```

Скрипт создаёт `src/data/factcheck/claims/<slug>.json` с массивом claims:
DATE_TEXT, DATE_DMY, DATE_YEAR, DATE_RANGE, MONEY, NPA_KOAP, NPA_FZ, LINK,
PERCENT. Каждый claim имеет `raw`, `context` (±80 символов), `line`,
`offset`.

### Шаг 1б — Смысловой проход: что regex не увидел

Регулярка находит только заранее перечисленные классы. Проверка
12.08.2026: абзац с семью проверяемыми утверждениями дал два — номер
постановления и дату. «Норматив ответа — 1,5 секунды», «штрафы выросли
втрое», «больше половины магазинов», «срок хранения — пять лет» не
попали никуда, потому что классов «длительность», «кратность», «доля» в
списке нет и не будет: список классов не замкнут.

Поэтому прочитай статью целиком и выпиши утверждения, которых нет в
`claims/<slug>.json`. Критерий один: **это утверждение о факте, которое
можно проверить по внешнему источнику**. Не мнение, не формулировка, не
обещание — факт.

Типичное, что пропускает regex: длительности и сроки («1,5 секунды»,
«пять лет», «в течение 30 дней»), кратности («втрое», «вдвое больше»),
доли («больше половины», «каждый третий»), количества («26 товарных
групп»), утверждения о состоянии рынка («большинство касс уже
поддерживают»).

Записать массивом в файл и влить:

```bash
node scripts/factcheck/extract-claims.mjs merge <slug> --file /tmp/<slug>-semantic.json
```

Формат: `[{ "raw": "точная цитата из статьи", "type": "DURATION",
"why": "зачем проверять" }]`. `raw` — **дословная цитата**, скрипт сам
найдёт её позицию и соберёт контекст. Цитату, которой в тексте нет,
скрипт отбросит и вернёт ненулевой код: проверять пересказ вместо
написанного — худший вид ложной уверенности.

### Шаг 2 — Категоризировать claims

Прочитать `src/data/factcheck/sources.json` — там маппинг типов claims на
канонические первоисточники + список заблокированных доменов (для них
работаем через WebSearch, а не WebFetch).

Решить для каждого claim:
- **Skip** — не нуждается в проверке (внутренняя ссылка на наш блог,
  ссылка на якорь и т.д.).
- **Check** — нужна проверка через WebFetch.
- **Search** — первоисточник в `blocked.domains` → используем WebSearch.

### Шаг 3 — Проверить каждый claim

Для каждого «Check» — `WebFetch` к первоисточнику, спросить актуальное
значение для контекста claim.

Для каждого «Search» — `WebSearch` с конкретным запросом, ориентирующимся
на claim. Шаблоны:
- **NPA_KOAP**: `"статья X.Y КоАП РФ 2026 [контекст из claim, например 'штраф ИП']"`
- **DATE_TEXT**: `"[тема статьи] [дата] постановление правительства"`
- **MONEY**: запросить вместе с упомянутой статьёй КоАП.

### Шаг 4 — Сравнить и записать результат

Отчёт больше не список утверждений: это связка, которую целиком
проверяет один валидатор (`scripts/factcheck/validate-bundle.mjs`), и его
же зовут маркер, гейт, релиз и CI. Пропустить часть нельзя — маркер не
выпишется.

**4.1. Снять снимок каждого первоисточника.** Цитата, выписанная по
памяти или из пересказа, не проходит: 21.08.2026 так в три статьи попал
несуществующий текст «пункта 16» ПП № 1944.

```bash
node scripts/factcheck/snapshot.mjs "<url>" --save --quote "дословная цитата"
```

Скрипт скажет, есть ли цитата на странице, и положит снимок в
`src/data/factcheck/snapshots/<sha256>.txt`. Хеш из вывода — в поле
`snapshotHash`. Без сохранённого снимка утверждение строгого класса не
принимается: валидатор пересчитывает хеш файла и ищет в нём цитату.

**4.2. Записать утверждения.** Поля каждого:

| Поле | Что это |
|---|---|
| `id` | адрес внутри отчёта (`r1`, `r2`, …) |
| `claimId` | **ссылка** в `claims/<slug>.json` — разные пространства имён |
| `raw` | цитата из статьи, ровно как в реестре извлечения |
| `statement` | что именно утверждается — предложением, не токеном |
| `subject`, `modality` | кого касается; обязывает/разрешает/запрещает/сообщает |
| `negated`, `conditions`, `effectiveFrom` | знак, условия, с какой даты |
| `span` | id единицы текста из `units` |
| `status`, `severity`, `confidence` | исход, вес, уверенность |
| `evidence[]` | `kind`, `sourceRole`, `url`, `locator`, `retrievedAt`, `effectiveAsOf`, `snapshotHash`, `quote`, `scope` |
| `sources[]` | адреса, на которых искали |
| `action`, `actionDetail` | что делать с текстом |

`status: match` совместим только с `action: keep`, и наоборот: нужна
правка — значит, значение не подтверждено. `skip` требует
`explanation`. `sourceRole: secondary` для строгого класса даёт максимум
`uncertain`, даже если страницу открывали целиком.

**4.3. Замкнуть реестр.** У каждого утверждения из
`claims/<slug>.json` должен быть ровно один исход: разбор в отчёте
(`claimId` ссылается на него) либо запись в `report.ledger`:

```json
"ledger": {
  "cf82cbe1d": { "outcome": "skipped", "reason": "адрес источника — работа аудита ссылок" },
  "c0a569226": { "outcome": "duplicateOf", "of": "caaf00f78" }
}
```

Утверждения, которого regex не увидел, в реестре нет — сначала влить:
`node scripts/factcheck/extract-claims.mjs merge <slug> --file <json>`.

**4.4. Классифицировать текст.** Каждое предложение, строка таблицы,
пункт списка и заголовок получают класс в `report.units`:

```json
"units": {
  "u7a1c3e90": { "class": "factual" },
  "u1b4d2f88": { "class": "non_factual", "reason": "связка между разделами" }
}
```

`factual` и `actionable` обязаны быть чьим-то `span`. `non_factual`
требует причины: «почему это не факт» — решение, а не умолчание.
Список единиц и их id: `node -e` через `scripts/factcheck/classify.mjs`.

**4.5. Печати.** `summary` не пишут руками — его считает
`computeOutcome`. `policyHash` и `contractVersion` проставляет
`write-marker`. `checkedBy` и `reviewedBy` для материалов
`riskTier: high` обязаны различаться: автор не подтверждает собственные
критические утверждения.

Записать в `src/data/factcheck/results/<slug>.json`.

### Шаг 5 — Создать маркер фактчека

`node scripts/factcheck/write-marker.mjs <slug>` — прогоняет связку
через тот же валидатор, что гейт, релиз и CI, и только потом пишет
`.claude/factchecked/<slug>`. Отказ означает, что чего-то из шага 4 не
хватает; сообщение называет, чего именно. Маркер — производная печать:
его можно удалить и пересоздать, вручную править нельзя. Используется `/maintain-content` как признак, что статья
прошла проверку; хеш привязывает маркер к конкретной версии текста —
правка после факчека делает маркер недействительным (pre-commit guard
это проверяет).

### Шаг 6 — Вывести отчёт

В чат выдать summary:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✔️ /factcheck <slug> — отчёт YYYY-MM-DD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Проверено N claims из M.

🔴 Критические расхождения (X):
  • [тип] «raw» — суть проблемы → действие

🟡 Средние (Y):
  • ...

🟢 Совпадает (Z)

📋 Рекомендации:
  1. ...
  2. ...

Полный JSON: src/data/factcheck/results/<slug>.json
```

## Когда статус — `mismatch` критической тяжести

Если найдено ≥ 1 `critical mismatch`:
1. **Не публиковать без правки.** Если у статьи `draft: false`, поставить
   `draft: true` обратно до исправления.
2. Предложить пользователю набор правок согласно `action`/`actionDetail`.
3. После применения правок — повторно запустить `/factcheck` (без аргумента
   или с тем же slug).

## Маркетинговый баланс — применяй редполитику

**Источник истины: `docs/editorial-policy.md`.** Не каждое расхождение
правится под букву первоисточника — там есть три класса правил.

Сценарий применения политики **в момент проверки**:

1. Прочитать `docs/editorial-policy.md` (правила классов A/B/C).
2. Для каждого расхождения подобрать правило по таблице «Что делает
   скилл автоматически».
3. Применить соответствующее `action`:
   - **Класс A** (`A1` суммы, `A2` номера НПА, `A3` техника, `A4` названия,
     `A5` юр. термины) → `severity: critical`, `action: rewrite-*`,
     откатить в `draft: true` если не исправлено.
   - **Класс B** (`B1` дедлайны, `B2` аудитория, `B3` тон, `B4` CTA,
     `B5` срочность) → `severity: moderate`,
     `action: add-disclaimer` / `keep`. Сохранить формулировку автора +
     добавить контекстный блок.
   - **Класс C** (`C1` внутренние ссылки, `C2` общие утверждения,
     `C3` якоря) → `status: skip`, в отчёт не пишем.

4. Если ситуация не подходит ни под одно правило — в отчёте поставить
   `status: needs-decision` и оставить редактору на ручное решение.

5. Если в процессе обнаружено типовое расхождение, не покрытое политикой
   — предложить пользователю добавить новое правило в
   `docs/editorial-policy.md`.

**Не изобретай решения на лету.** Если нет правила — лучше
`needs-decision`, чем самостоятельная интерпретация. Политика прирастает
явно, через коммиты.

## Ограничения

- WebFetch блокируется на consultant.ru, pravo.gov.ru, yandex.* — берём тот же
  документ там, где он доступен: base.garant.ru, rulaws.ru,
  publication.pravo.gov.ru, сайт профильного ведомства. **Сниппет выдачи
  доказательством значения не является**: для строгого класса (суммы, сроки и
  даты вступления, проценты, ответственность, указания к действию, номера НПА,
  теги и версии форматов) он даёт только `uncertain`. Гейт `check-report.mjs`
  такое утверждение как `match` не примет — и это не обходится, а решается
  дословной цитатой с полученной страницы.
- Скрипт извлечения работает по regex — может пропустить нестандартные
  упоминания (например, «по статье пятнадцать двенадцать»). Это нормально:
  фактчек — не замена редактору, а первый фильтр.
- Один прогон ≈ 10 WebSearch + 0–5 WebFetch. Для batch (#39 в backlog) —
  параллельный subagent dispatch.

## Доказательство, а не вердикт

13.08.2026 редактор прислала разбор статьи «Ошибки ТС ПИоТ», сделанный
сторонней моделью: шесть существенных фактических ошибок. Наш отчёт по
этой же статье стоял `passed`, `criticalIssues: 0`, 35 из 38 утверждений
«совпало». Занижённые почти в полтора раза пороги ст. 171.1 УК РФ
прошли с уверенностью 0.85, неверный номер тега ФФД — как `minor`.

Причина не в невнимательности. Проверялся **токен**, а не утверждение:
из текста извлекалось «400 000 ₽» или «54-ФЗ», и подтверждалось, что
норма существует, а число где-то встречается. Само утверждение статьи
никто не формулировал, а значит и не проверял.

Поэтому по каждому утверждению, где ошибка имеет последствия — деньги,
сроки, статьи КоАП и УК, номера тегов и реквизитов, — в отчёт пишутся
четыре поля:

| Поле | Что в нём | Зачем |
|---|---|---|
| `statement` | Что именно утверждает статья, целиком | «400 000 ₽» проверить нельзя; «крупный размер по ст. 171.1 УК для продовольственных — от 400 000 ₽» можно |
| `quote` | **Дословная** цитата первоисточника с этим значением внутри | Не можешь привести цитату с числом — не проверил число |
| `sources` | Ссылка на первоисточник: pravo.gov.ru, consultant, garant, сайт ведомства | Отраслевой портал и инструкция поддержки пересказывают норму, а порог берётся из текста нормы |
| `confidence` | Согласована со статусом | Критическое ниже 0.8 и значимое ниже 0.7 не может быть «совпало» |

Проверяет это `node scripts/factcheck/check-report.mjs <slug>`. Пока
отчёт не проходит проверку, `write-marker` **не выпишет маркер** — а без
маркера статья не пройдёт гейт. Ненулевой код здесь означает не «статья
плоха», а «проверка не доказана».

**Severity ставит тот же, кто проверяет**, поэтому гейт на неё не
полагается: опасность определяется по содержанию утверждения. Число тега,
кода, реквизита или упоминание штрафа делают утверждение строгим
независимо от того, какую важность ему присвоили.

Пример честно собранного утверждения:

```json
{
  "id": "c31", "type": "MONEY", "raw": "2 250 000 ₽",
  "statement": "крупный размер по ст. 171.1 УК РФ для непродовольственных товаров — свыше 2 250 000 ₽",
  "status": "match", "severity": "critical", "confidence": 0.95,
  "quote": "признаются совершёнными в крупном размере, если стоимость немаркированных товаров превышает 2 250 000 рублей",
  "sources": ["http://publication.pravo.gov.ru/document/..."]
}
```

## Полнота: ничего не пропущено

Доказательства защищают то, что в отчёт попало. Второй способ ошибиться —
не вспомнить про факт вовсе: утверждение в статье есть, в отчёте его нет,
проверять нечего, и отчёт честно зелёный. Так 13.08.2026 прошла
ст. 15.12.1 КоАП РФ. **Отсутствующее не оставляет следа**: 38
утверждений, все с источниками, все подтверждены.

```bash
node scripts/factcheck/check-coverage.mjs <slug>
```

Сверяет статью с отчётом: каждая сумма, дата, ссылка на норму, номер
тега и процент из текста обязаны найтись среди разобранного. Не найдены —
маркера не будет.

Из сверки намеренно исключены frontmatter, адреса и подписи ссылок,
маркеры промоблоков и врезок, нумерация списков: проверка, ругающаяся на
номер пункта, будет выключена за неделю, и тогда она не сработает и в
настоящий раз.

**Чего сверка не умеет.** Она сравнивает статью с отчётом, а не мир со
статьёй. Норма, которую следовало упомянуть, но которой в тексте нет,
здесь не всплывёт — это работа ресёрча и редактора.
