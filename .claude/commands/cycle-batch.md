# /cycle-batch — рутина C: батч статей в Google Docs

Запускается **дважды в неделю** — понедельник и четверг, утро.
Пишет `batchSize` статей за раз (сейчас 5), каждую в отдельный Google Doc
в папке цикла. Точное число берётся из состояния цикла, не из этого файла.

Два запуска по 5 статей — это ~43 статьи в месяц, потолок выработки.

---

## Шаг 0 — Предохранитель

```bash
node scripts/cycle-state.mjs can-start-batch
```

**Ненулевой код — СТОП**, вывести причину и завершиться молча.

| Вывод | Что происходит |
|---|---|
| `план ещё не одобрен в таблице` | Ждём согласования, ход за редактором |
| `у редактора на вычитке 10 статей (потолок 10)` | Очередь забита, ждём приёмки |
| `botских тем в очереди нет` | Осталось только то, что редактор пишет сам |
| `цикл в состоянии idle/done` | Активного цикла нет |

Потолок `maxInReview` (сейчас 10) — это и есть защита от заваливания
редактора: когда очередь полна, следующая порция не стартует. Никогда не
обходить эту проверку. Значение живёт в состоянии цикла и меняется
командой `cycle-state.mjs set-limits`, в этот файл его не вшивать.

---

## Шаг 1 — Отобрать темы

```bash
node scripts/cycle-state.mjs next-batch --size 3
```

Возвращает темы со статусом `planned` и `owner: bot`, отсортированные
P0 → P1 → P2. Размер сам ужимается под остаток места в очереди редактора:
если влезает только 2 — вернёт 2.

Темы «пишем сами» сюда не попадают никогда.

---

## Шаг 1а — Развилка: статья или актуализация

У каждой темы в выводе `next-batch` есть поле `kind`:

| `kind` | Что это | Куда идёт |
|---|---|---|
| `new` (или поля нет) | Новая статья | Шаги 1б → 3 → 4, `/create-article` |
| `update` | Актуализация чужой статьи Маркета | `/update-article <slug>`, шаги 1б и 3 пропускаются |

Задача на актуализацию узнаётся по ячейке «Тема»: редактор пишет
«Актуализировать статью <ссылка> …» и дальше просьбу. Разбор делает
`lib/update-task.mjs`, гадать по тексту в сессии не нужно —
`sourceUrl`, `brief` и `refUrls` уже лежат в теме.

**По задаче на актуализацию новая статья не пишется никогда.** Результат
— документ правок в `src/content/updates/`. Полная процедура и правила
— `.claude/commands/update-article.md`.

Батч смешанный: в одной порции может быть три новых статьи и две
актуализации. Ёмкость очереди они занимают одинаково.

---

## Шаг 1б — дубль проверяется до ресёрча, не после

Только для тем с `kind: new`. Для актуализации проверка на дубль
работает иначе — см. шаг 3 в `/update-article`.

По каждой теме батча, **до запуска research-specialist**:

```bash
node scripts/audit/check-draft-duplication.mjs "<тема>"
```

Коды: `0` — чисто, пиши. `1` — дубль. `2` — пограничное совпадение.

**Решение принимается по правилу, а не вопросом владельцу:**

| Код | Что делать |
|---|---|
| `1`, найденный текст — черновик | Новую статью не писать. Довести существующий черновик до полного пайплайна (факчек, SEO, оценка) и завести его в цикл как результат по этой теме: `cycle-state.mjs set-doc` и дальше как обычно |
| `1`, найденный текст выпущен | Тему снять: `cycle-state.mjs` через решение «убрать», в отчёте — ссылка на существующую статью и пометка «кандидат на обновление» |
| `2` | Писать, но сузить угол и сослаться на найденный материал. В отчёте назвать, чем отличается |

Это правило появилось 13.08.2026: рутина остановилась посреди батча,
обнаружив, что тема «Касса от банка или отдельно» повторяет черновик
четырёхдневной давности, и спросила владельца, что делать. Вопрос был
правильный, момент — нет: ресёрч уже шёл, батч встал на несколько часов.

**Останавливаться и спрашивать — только если правило не покрывает
случай.** Всё, что покрывает, решается сразу и пишется в отчёт: что
нашлось, какое правило применили, что из этого вышло.

## Шаг 2 — Пометить в работе

```bash
node scripts/cycle-state.mjs start-batch --slugs <slug1,slug2,slug3>
node scripts/cycle-state.mjs sheet-sync > /tmp/cells.json
node scripts/drive-sync.mjs set-cells --sheet-id <sheetId> --updates "$(cat /tmp/cells.json)"
```

Редактор видит в таблице «пишется» и понимает, что происходит.

## Шаг 3 — Написать статьи

Для темы с `kind: new` — полный `/create-article "<title>"`, все девять
стадий со шлюзами. Не сокращать пайплайн ради скорости.

Для темы с `kind: update` — `/update-article <slug>`. Это другой жанр и
другой набор проверок: `check-update-doc` вместо `check-seo` и
`analyze-article`. Не подменять актуализацию новой статьёй на ту же
тему, даже если так получается быстрее и оценка выходит выше.

Статьи сохраняются в `src/content/blog/`, документы правок — в
`src/content/updates/`, и те и другие с `draft: true`. Репозиторий
остаётся источником истории версий.

**Обработка сбоев по одной статье:**

- Не прошла шлюз после 2 попыток — не блокировать остальные. Вернуть тему
  в `planned` и записать причину для отчёта.
- Прошла хотя бы одна — батч уходит редактору.
- Не прошла ни одна — доков не создавать, написать в таблицу и в отчёт.

**Бюджет сессии.** Три полных `/create-article` — это много. Если видно,
что сессия не дотянет, довести текущую статью, выложить готовое и
завершиться. Недописанные темы остаются `planned` и попадут в четверг.

## Шаг 4 — Выложить в Google Docs

Для каждой написанной статьи:

```bash
node scripts/drive-sync.mjs make-doc \
  --title "<Заголовок статьи>" \
  --md src/content/blog/<файл>.md \
  --folder <drive.folderId>
```

Скрипт возвращает `docId` и `url`. Frontmatter в док не попадает —
перед выкладкой отрезать его, редактору служебные поля не нужны.

В начало дока добавить короткую врезку для вычитки:

```markdown
## Как вычитывать

Правьте текст прямо здесь — это рабочая версия. Спорные места
отмечайте комментариями, я отвечу в течение 4 часов.

Когда статья устроит — поставьте «принято» в колонке «Решение»
строки темы в таблице плана (не в колонке «Статус» — та моя).
Дальше я заберу текст в репозиторий.

Проверено автоматически: факт-чек зелёный, ссылки на НПА
действующие, check-ai N/10, оценка NN/100, слов NNNN.
```

Привязать док к теме:

```bash
node scripts/cycle-state.mjs to-review --slug <slug> \
  --doc-id <docId> --doc-url <url>
```

## Шаг 5 — Обновить таблицу и состояние

```bash
node scripts/cycle-state.mjs sheet-sync > /tmp/cells.json
node scripts/drive-sync.mjs set-cells --sheet-id <sheetId> --updates "$(cat /tmp/cells.json)"

git add src/content/blog src/content/updates src/data/editorial-cycle.json
git commit -m "cycle: батч N — <k> статей на вычитку"
git push -u origin main
```

Статусы в таблице становятся «на вычитке», в колонке «Документ» —
ссылки. Редактору больше ничего искать не нужно.

## Шаг 6 — Позвать редактора

По каждому свежесозданному доку:

```bash
node scripts/drive-sync.mjs notify --file-id <docId> --to <ящик редактора> \
  --message "Статья на вычитке: <заголовок>. Решение ставится в таблице плана, колонка «Решение»."
```

Письмо шлёт Google при выдаче доступа — это единственный надёжный канал
до почты редактора. Уходит только при первой выдаче доступа к файлу,
поэтому зовём по новым докам, а не по таблице плана: по ней доступ уже
есть, и `notify` честно вернёт код 2 вместо письма.

Ящик редактора — тот же, на который расшарена корневая папка (см.
`docs/editorial-cycle.md`, врезка про уведомления). Ящика нет — шаг
пропускается, и это пишется в отчёт: значит редактор о батче не узнает.

Дополнительно — комментарий в таблице, чтобы вопрос был виден и в файле:

```bash
node scripts/drive-sync.mjs comment --file-id <sheetId> \
  --text "Батч N: <k> статей на вычитке, ссылки в колонке «Документ»." \
  --mention <ящик редактора>
```

Это не замена `notify`: письма по упоминанию Google не гарантирует.

Затем — одно сообщение на батч в отчёт сессии, не три:

```
Батч N готов к вычитке — <k> статей:

1. <Заголовок> — <ссылка на док>
2. <Заголовок> — <ссылка на док>
3. <Заголовок> — <ссылка на док>

Таблица плана: <sheetUrl>
У вас на вычитке всего: N из 6. Осталось тем в цикле: M.
```

## Правила

- `can-start-batch` не обходить никогда.
- `batchSize` статей (сейчас 5), меньше — если очередь редактора почти полна.
- Темы «пишем сами» не трогать.
- `kind: update` — только `/update-article`, новую статью не писать.
- Frontmatter в Google Doc не выкладывать.
- Статьи остаются `draft: true`. Снимает флаг рутина B, когда редактор
  поставит «принято» в таблице.
- Сбой одной статьи не отменяет батч.
- Язык — только русский.
