# /create-article — создание статьи

**Процесс 2 из 4.** Запускается по теме из редкалендаря.
Результат — статья в `draft: true`, прошедшая все проверки, с hero-изображением.

Вызов: `/create-article "штраф за работу без ТС ПИоТ в 2026"`

Передача редактору — через `/cycle-batch`.
Для быстрого черновика без шлюзов — `/new-post`.

---

## Статус

```
▶ /create-article "<тема>"
━━━━━━━━━━━━━━━━━━━━━━━━━━━
Стадия 1/9: DISCOVERY
```

---

## Стадия 1 — DISCOVERY

1. Прочитать `src/content/wiki/content-plan-2026.md` — найти тему, уточнить целевой запрос.

2. Проверить дублирование: прочитать frontmatter всех `src/content/blog/*.md`.
   Если пересечение по смыслу > 70% — СТОП, предложить варианты.

3. **Определить, попадает ли тема в категорию с НПА:**
   - `ts-piot` → ПП № 1944, 54-ФЗ
   - `markirovka` → отраслевые ПП Правительства, ст. 15.12 КоАП, ст. 171.1 УК
   - `zakonodatelstvo` → НК РФ, ТК РФ, КоАП, ФЗ
   - `egais` → ст. 14.16/14.17/14.19 КоАП, 171-ФЗ
   - `kkt` → 54-ФЗ, ст. 14.5 КоАП

   Если категория попадает в этот список — **research-specialist обязателен.**
   Без research-brief writer не запускается. Это страховка от галлюцинаций
   номеров НПА (за прошлые сессии выявлено 3 фейковых ПП).

4. Запустить агент `research-specialist`. Сохранить brief:
   `.claude/research/YYYY-MM-DD-slug-brief.md`. Bief должен содержать
   frontmatter с массивом `sources[]`, каждый элемент с `verified: true`
   (агент физически проверяет норму через WebFetch/WebSearch).

**Шлюз 1:**
```
[ ] Тема не дублирует существующие статьи?
[ ] Категория с НПА → research-brief обязателен; иначе пропуск разрешён?
[ ] Brief содержит ≥ 3 источника с НПА/датами?
[ ] Все sources[] в brief frontmatter имеют verified: true?
[ ] Есть целевой поисковый запрос?
```

---

## Стадия 2 — WRITE

Запустить агент `content-writer` с research brief.

Требования:
- 1200–2500 слов, структура: лид → 5–7 H2 → FAQ (≥ 4 вопроса) → заключение
- ≥ 3 внутренних ссылки, ≥ 1 ссылка на НПА
- Frontmatter по шаблону из CLAUDE.md, `draft: true`

Сохранить: `src/content/blog/YYYY-MM-DD-slug.md`

**Шлюз 2:**
```
[ ] Файл создан и парсится без ошибок?
[ ] Frontmatter полный (title, description, pubDate, tags, categories, seo.keywords)?
[ ] Тело статьи ≥ 1000 слов?
```

---

## Стадия 2а — АВТОПЕРЕЛИНКОВКА

После того как `content-writer` положил статью, прогоняем
`node scripts/audit/linkgraph.mjs` чтобы пересобрать граф ссылок. Затем:

1. **Исходящие ссылки из новой статьи.** Скорим существующие статьи по
   совпадению `categories` (×2) + `tags` (×1) с новой. Берём топ-5
   кандидатов. Если в тексте нет ссылки на них — предлагаем места
   вставки (упоминание термина / название продукта / смежная тема).

2. **Входящие ссылки на новую статью.** Из отчёта `linkgraph.json` берём
   список текущих сирот в той же категории + слабых (1 входящая).
   Если категория совпадает и тема релевантна — открываем 2–3 статьи-донора
   и предлагаем точечный edit: «упомянуть новую статью с anchor-текстом
   из её title».

3. Минимум 3 исходящих + 1 входящая ссылка должны появиться **до**
   следующей стадии. Если меньше — `content-writer` дополняет тело.

**Шлюз 2а:**
```
[ ] У статьи ≥ 3 исходящих внутренних ссылок?
[ ] В минимум 1 существующей статье добавлена ссылка на новую?
[ ] linkgraph.mjs пересобран; новая статья не в orphans?
[ ] Органическое упоминание продукта Контура с гиперссылкой (если уместно)?
```

---

## Стадия 2б — CALLOUTS

Прочитать статью. Найти 1–2 факта для врезок:
- `callout--penalty` — если есть конкретные суммы штрафов
- `callout--date` — если есть ключевая дата вступления в силу
- `callout--warning` — если есть критическое требование
- `callout--tip` — если есть пошаговый раздел

Вставить через `<div class="callout callout--TYPE">...</div>`.
Контент — только из текста статьи, не придумывать.

**Шлюз 2б:** не более 2 врезок, факты только из текста.

---

## Стадия 3 — FACTCHECK

1. Прогнать NPA-аудит: `node scripts/factcheck/audit-npa-references.mjs --strict`.
   Если в статье есть упоминания ПП/Приказов/ФЗ, которых нет ни в whitelist
   `src/data/factcheck/sources.json`, ни на pravo.gov.ru — это критическое
   расхождение. Прежде чем запускать `/factcheck`, исправь номера или
   расширь whitelist.

2. Запустить `/factcheck <slug>` (наш собственный стек, не плагин claude-blog).
   Скилл извлекает claims, сверяет с первоисточниками, применяет редполитику
   из `docs/editorial-policy.md` (классы A/B/C). Подробности —
   `docs/factcheck.md`.

**Шлюз 3:**
```
[ ] audit-npa-references.mjs --strict зелёный?
[ ] Нет claims с confidence < 0.7 без пометки [нужна проверка]?
[ ] Все даты сроков подтверждены источником?
[ ] Суммы штрафов соответствуют актуальной редакции КоАП?
[ ] Все ПП/Приказы/ФЗ в статье — из npaWhitelist или brief.sources[]?
```

При провале — таблица слабых claims → правки → повтор. Максимум 2 попытки.

## Стадия 4 — РЕДПОЛИТИКА + CHECK-AI

Сверить статью с CLAUDE.md (разделы «Правила контента», «Стиль речи»).
Затем запустить детекцию AI-маркеров:

```bash
node scripts/check-ai-markers.mjs src/content/blog/SLUG.md
```

Если скор ≥ 6 — переписать проблемные секции до повторного прогона.

**Шлюз 4 (ключевые точки отказа):**
```
Объём:
[ ] ≥ 800 слов (сателлит) или ≥ 1500 (опорная)

Структура:
[ ] ≥ 4 H2, FAQ ≥ 4 вопросов, заключение с внутренними ссылками
[ ] H2-заголовки информативны, понятны без контекста

Frontmatter:
[ ] title: 50–80 символов
[ ] description: 140–160 символов
[ ] reviewDate: через 6 месяцев от pubDate
[ ] tags: 4–7 штук, строчные
[ ] categories: одна из [ts-piot, kkt, markirovka, egais, zakonodatelstvo]

Стиль (редполитика kontur.ru):
[ ] Нет слов-паразитов: является, осуществляет, в целях, таким образом, данный
[ ] Нет канцеляризмов: во избежание, посредством, надлежащим образом
[ ] Обращение «вы» строчной буквой
[ ] Нет эмодзи, восклицательных знаков, оценок без фактов
[ ] Активный залог, прямое обращение к читателю

Check-AI:
[ ] node scripts/check-ai-markers.mjs — скор < 6?
[ ] Нет структурных AI-паттернов (все абзацы одной длины, обобщения без примеров)?
```

## Стадия 5 — SEO

Запустить агент `seo-optimizer`.

**Шлюз 5:**
```
[ ] Целевой ключ в title (H1), первом абзаце, хотя бы одном H2?
[ ] description: 140–160 символов, содержит ключ + ценностный крючок?
[ ] Год «2026» в title или description?

```

## Стадия 6 — КАННИБАЛИЗАЦИЯ

Сравнить `seo.keywords` новой статьи с ключами опубликованных статей.

**Шлюз 6:** пересечение < 50% с любой существующей, нет совпадения H1.

При провале — СТОП, предложить варианты A (merge) / B (differentiate) / C (canonical).

## Стадия 7 — ВИЗУАЛ И ПРОМО (текстовый бриф)

Модуль не рисует картинки и не собирает страницы — изображения делает
принимающий проект. Задача стадии — отдать ему готовый бриф, чтобы не
пришлось придумывать заново.

Раньше здесь предписывался запуск workflow «Generate Hero Images». Такого
workflow в репозитории нет и не было (`.github/workflows/` — только два
файла Wordstat), каталога `public/` тоже нет. Стадия отработать не могла.

Результат — файл `src/data/visuals/<slug>.md`, коммитится вместе со
статьёй. Не класть в `.claude/research/` или `.claude/social/`: они в
`.gitignore`, файл потеряется при следующей сессии.

### 8.1 — ТЗ на hero-изображение

Текстом, без картинки:

- Сюжет: что изображено, какое действие происходит.
- Ключевой объект в кадре (касса, коробка с кодом Data Matrix, документ).
- Настроение и тон, что должно считываться за секунду.
- Чего не должно быть: людей крупным планом, узнаваемых логотипов,
  текста на изображении.
- Формат: горизонтальный, безопасная зона под наложение заголовка.

### 8.2 — Иллюстрации в тело статьи

2–4 предложения, привязанные к конкретным H2. По каждому:

- К какой секции относится.
- Тип: схема процесса, скриншот интерфейса, таблица-картинка, фотография.
- Что именно показать и зачем — какой абзац текста картинка разгружает.

Не предлагать иллюстрацию туда, где таблица в тексте уже справляется.

### 8.3 — Подводки к промоблокам (CPA)

**Три штуки на статью.** Подводка — это текст-переход от содержания
статьи к офферу, а не пометка «здесь баннер». Писать так, чтобы читатель
не спотыкался: подводка продолжает мысль абзаца, после которого стоит.

По каждой: после какой секции, текст подводки (1–2 предложения), какая
задача читателя в этот момент закрыта и что логично предложить дальше.

Точность попадания в лучшее место не требуется — достаточно накидать
кандидатов, финальную расстановку делает принимающий проект.

> **Типы CPA-блоков пока не заданы.** Пользователь предоставит список
> отдельно; до тех пор описывать оффер по смыслу («подбор кассы под
> требования из этого раздела»), а не по названию блока. Когда список
> появится — добавить его сюда и ссылаться на конкретные типы.

**Шлюз 7:**
```
[ ] src/data/visuals/<slug>.md создан?
[ ] Есть ТЗ на hero?
[ ] Есть привязка иллюстраций к конкретным H2?
[ ] Ровно 3 подводки к промоблокам, каждая с текстом перехода?
```

## Стадия 8 — ОЦЕНКА

Идёт последней, после брифа на визуал: `/analyze-article` проверяет в том
числе наличие `src/data/visuals/<slug>.md`, поэтому запускать его раньше
Стадии 7 бессмысленно — упрётся в то, чего ещё не сделали.

Запустить `/analyze-article <slug>` — единственная шкала оценки в проекте
(0–100 по 6 категориям). Своей шкалы у этой стадии нет: тот же гейт
работает и здесь, и перед передачей редактору, чтобы статья не проходила
локальную проверку и не падала на финальной.

**Шлюз 8:** балл ≥ 70 и `blocker: false` в `src/data/analyze/<slug>.json`.

При провале — взять из отчёта список конкретных недостатков, внести
правки, перезапустить `/analyze-article`. Учти, что он проверяет и то,
чего нет в более ранних шлюзах: полноту frontmatter, свежесть
factcheck-маркера, бэклинк на pillar (если у кластера есть опорный
материал).

---

## Стадия 9 — ГОТОВО

Убедиться, что `draft: true` (публикация — отдельный шаг `/release-article`).

Обновить editorial-plan.json (если в Стадии 1 статья была добавлена в контент-план):
```
node scripts/generate-editorial-plan.mjs
```

Закоммитить черновик:
```
git add src/content/blog/SLUG.md src/data/visuals/SLUG.md src/data/editorial-plan.json
git commit -m "draft: [title]"
git push
```

`.claude/research/` в `.gitignore` — брифа ресёрча в коммите не будет,
это ожидаемо. А `src/data/visuals/SLUG.md` добавить обязательно: он
нужен принимающему проекту и проверяется в Стадии 8.

## Правила

- Никогда не пропускать стадии.
- Максимум 2 retry на стадию — затем СТОП с объяснением.
- Revision-агент получает только список конкретных проблем.
- Не устанавливать `draft: false` — это делает `/release-article`.
- Язык — только русский.
