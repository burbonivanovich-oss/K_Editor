# /cycle-listen — рутина B: слушатель редактора

Запускается каждые 4 часа по будням в свежей сессии. Единственная точка,
где человеческая обратная связь попадает в пайплайн.

**Главное правило: нового нет — завершиться молча.** Рутина срабатывает
~20 раз в неделю; уведомление должно приходить только когда что-то
действительно произошло.

Редактор работает **только в Google Drive**. GitHub он не открывает.

**Очередь запросов из таблицы.** Редактор жмёт пункт меню «Контур» в
Google-таблице, запрос падает в `src/data/editor-requests/*.json` с
`handled: false`. Эти файлы разбираются **первыми** — до обхода таблицы —
и ответ по ним даётся всегда, даже если в остальном проход пустой и по
общему правилу следовало бы завершиться молча. Кто-то ждёт ответа к
дедлайну: это единственный случай, когда молчать нельзя.

Разобрали — проставить `handled: true` и закоммитить, иначе следующий
проход возьмёт запрос повторно.

Устройство кнопки — `docs/editor-button.md`.

---

## Шаг 0 — Что сейчас

```bash
node scripts/cycle-state.mjs get --json
```

`idle` или `done` — выйти молча.

---

## Шаг 0а — Очередь запросов из таблицы

```bash
ls src/data/editor-requests/*.json 2>/dev/null
```

Каждый файл с `handled: false` — нажатая редактором кнопка. Поля: `kind`
(`urgent` / `question` / `recheck`), `topic`, `note`, `who`, `at`.

Разбирать до таблицы и отвечать по каждому:

- `urgent` — сделать правку в первую очередь, ответить в треде дока темы.
- `question` — ответить в треде, ничего не переписывая.
- `recheck` — перечитать док темы: правки внесены, замечания могли
  закрыться.

После обработки — `handled: true` в файле и коммит. Непроставленный флаг
означает, что на следующем проходе тот же запрос разберут заново и
редактор получит второй ответ на тот же вопрос.

Очередь пуста — идти дальше молча, это обычное состояние.

## Шаг 1 — Прочитать таблицу

```bash
node scripts/drive-sync.mjs pull --sheet-id <drive.sheetId> > /tmp/pull.json
node scripts/cycle-state.mjs apply-decisions --file /tmp/pull.json
```

`apply-decisions` возвращает JSON с разбором:

```json
{
  "approved": true,
  "dropped": ["ЕНС для ИП"],
  "toEditor": ["Маркировка воды с 01.09.2026"],
  "accepted": [{ "slug": "...", "title": "Штраф за работу без ТС ПИоТ" }],
  "notes": [{ "slug": "...", "title": "...", "note": "переформулировать под общепит" }],
  "added": ["Кассовый чек: реквизиты 2026"],
  "missing": []
}
```

Что с этим делать:

| Поле | Действие |
|---|---|
| `approved: true` | Шаг 2 — план едет в репозиторий |
| `accepted` | Шаг 6а — забрать текст из дока темы в репозиторий |
| `rejected: true` | `reset --force`, записать причину в `src/content/wiki/`, сообщить |
| `dropped` | Уже применено скриптом, только упомянуть в отчёте |
| `toEditor` | Шаг 4 — создать пустой док с брифом |
| `added` | Уже в плане; дособрать обоснование и частотность по новой теме |
| `notes` | Шаг 3 — разобрать свободный текст |
| `missing` | Редактор удалил строку целиком. Пометить тему `dropped` через `apply-decisions` не получится — снять вручную и сообщить |
| `designBrief` | Редактор заказал ТЗ дизайнеру по готовому тексту — шаг 6в |
| `paused` | В B2 стоит «ПАУЗА до дд.мм.гггг» — редактор остановил новые батчи. Разбор решений и ответы на комментарии продолжаются, останавливается только рутина C. Упомянуть в отчёте и не считать сбоем |
| `resumed` | Пауза снята, конвейер снова идёт |
| `unrecognized` | Колонка «Решение» — не строгий список: Sheets примет любой текст, ячейка только подсказывает. Значение не совпало ни с одним известным («убрать» / «пишем сами» / «одобрено» / «принято») — типичная причина: опечатка или синоним. Оставить комментарий через `drive-sync.mjs comment` с уточнением и указанием строки, тему не трогать — то же правило, что и для непонятной «Правки» (шаг 3) |

Если всё пусто и `approved` не сменился — выйти молча.

## Шаг 2 — Согласование плана

Только здесь контент-план в репозитории впервые меняется:

1. Записать темы в `src/content/wiki/content-plan-2026.md` по кластерным
   разделам с пометкой `# [cycle-plan YYYY-MM-DD, согласовано]`.
2. `node scripts/generate-editorial-plan.mjs`.
3. Закоммитить `cycle: план <YYYY-MM> согласован`, запушить.
4. Синхронизировать статусы обратно в таблицу (шаг 5).

Состояние уже переведено в `running` скриптом.

## Шаг 3 — Свободный текст из колонки «Правка»

Понимать по смыслу, не по синтаксису:

| Редактор написал | Действие |
|---|---|
| «подними приоритет» | Поправить `priority` темы в состоянии |
| «переформулировать на ...» | Уже применено, если он поправил ячейку «Тема». Иначе поправить |
| «добавь про штрафы» | Учесть при написании — дописать в `rationale` |
| «уже писали в мае» | Проверить, найти статью, при подтверждении снять тему |
| Вопрос | Ответить комментарием к ячейке через Drive API |

**Непонятную формулировку не угадывать.** Оставить комментарий с
уточняющим вопросом и не трогать тему:

```bash
node scripts/drive-sync.mjs comment --file-id <sheetId> \
  --text "Строка N, колонка «Правка»: <что именно непонятно>?" \
  --mention <ящик редактора>
```

Привязать комментарий к конкретной ячейке API не даёт — `anchor` для
Sheets не документирован. Поэтому строку и колонку называем словами в
самом тексте, иначе редактору придётся угадывать, о чём вопрос.

## Шаг 4 — Темы «пишем сами»

Редактор поставил «пишем сами» — статью пишут люди, бот только готовит
почву. Для каждой такой темы:

1. Прогнать `/research-topic "<тема>"` — собрать НПА, сроки, штрафы,
   источники.
2. Собрать markdown-бриф: целевой запрос, структура H2, ключевые факты
   со ссылками на первоисточники, что обязательно упомянуть, требования
   редполитики Контура, минимум 3 внутренние ссылки с предложенными
   анкорами.
3. Создать док в папке цикла:

```bash
node scripts/drive-sync.mjs make-doc \
  --title "<Заголовок>" --md /tmp/brief.md --folder <drive.folderId>
```

4. Привязать док к теме:

```bash
node scripts/cycle-state.mjs to-review --slug <slug> \
  --doc-id <id> --doc-url <url>
```

`to-review` тоже упирается в потолок `maxInReview` — тема «пишем сами»
занимает то же место в очереди редактора, что и ботовская. Если команда
отказала («потолок очереди»), доку из шага 3 уже некуда идти прямо
сейчас: подождать, пока `count(review)` освободится, и повторить
`to-review` позже — сам док и бриф от повтора не страдают.

Дальше люди пишут прямо в доке. Когда поставят в таблице «принято» —
статья импортируется тем же путём, что и ботовская (шаг 6).

## Шаг 5 — Синхронизировать статусы в таблицу

```bash
node scripts/cycle-state.mjs sheet-sync > /tmp/cells.json
node scripts/drive-sync.mjs set-cells --sheet-id <sheetId> --updates "$(cat /tmp/cells.json)"

node scripts/cycle-state.mjs row-decisions > /tmp/rows.json
node scripts/drive-sync.mjs set-row-dropdowns --sheet-id <sheetId> --updates "$(cat /tmp/rows.json)"
```

Колонки «Статус» и «Документ» — зеркало состояния. Редактор по ним
понимает, что происходит, не спрашивая. Строка состояния в шапке (E2)
пишется тем же вызовом.

`set-row-dropdowns` подгоняет список решений под статус каждой строки: у
темы в плане — «одобрено / убрать / пишем сами», у статьи на вычитке —
«принято / убрать», у принятой — «нужно ТЗ дизайнеру». Общий список из
шести значений заставлял редактора помнить, что где применимо, и молча
допускал бессмысленные комбинации вроде «пишем сами» для уже написанной
статьи. Списки нестрогие: вписать своё значение по-прежнему можно.

## Шаг 6 — Статьи на вычитке

Для каждой темы в статусе `review` с `docId`:

### 6а. Редактор принял

Тема есть в `changes.accepted` из шага 1 (`apply-decisions`) — это
единственный сигнал приёмки: редактор поставил `принято` в колонке
«Решение». Колонку «Статус» рядом не читать как признак приёмки — это
ботовская колонка, `sheet-sync` пишет туда `принято` уже ПОСЛЕ обработки,
как подтверждение, а не как вход.

Забрать текст из дока обратно в репозиторий:

```bash
node scripts/drive-sync.mjs export-doc --doc-id <id> --out /tmp/<slug>.md
```

Записать в журнал то, что редакция поправила руками — **до** того, как
файл в репозитории перезапишется экспортом:

```bash
node scripts/editor-edits.mjs record --slug <slug> --doc /tmp/<slug>.md
```

Прямая правка в доке — такая же обратная связь, как комментарий, но без
этого шага она исчезает: текст уезжает в репозиторий, и в следующей
статье бот пишет ту же формулировку.

Скрипт видит разницу, но не понимает её. Смысл называешь ты:

```bash
node scripts/editor-edits.mjs pending
```

Команда покажет записи без вывода. По каждой прочитай пары «было/стало»
и допиши под записью одну строку:

```
**Вывод:** редакция убирает пассив в лиде и ставит конкретную сумму вместо «значительных штрафов»
```

Вывод — про закономерность, а не про эту статью. «Поправили опечатку» —
не вывод; «редакция всегда выносит дату в первое предложение» — вывод.
Не видно закономерности — так и напиши: `**Вывод:** разовая правка`.
Врать про систему хуже, чем признать единичный случай.

Один и тот же вывод третий раз — это уже не наблюдение, а правило:
предложи его в `docs/content-rules.md` и скажи об этом в отчёте. Разовая
правка живёт одну статью, правило — весь корпус.

Дальше — путь зависит от того, кто тему писал (`owner` в состоянии):

**Тема `owner: bot`.** Файл `src/content/blog/YYYY-MM-DD-<slug>.md` уже
существует и уже закоммичен — его создал `/create-article` в рутине C
(шаг 4 `/cycle-batch`), с полным frontmatter (title, description, tags,
categories, seo.keywords) и `draft: true`. **Не восстанавливать
frontmatter заново** — состояние цикла эти поля не хранит, а
придумывать их заново на этом шаге значит терять то, что уже подобрал
`seo-optimizer` при написании, и рискует не пройти P0-проверки
`check-seo.mjs` (pre-commit гейт). Вместо этого:

1. Взять существующий файл, заменить **только тело** на экспорт из дока
   (это правки редактора) — frontmatter из файла не трогать, кроме:
   `draft: true → false`, и `updatedDate` — если тело менялось.
2. Сохранить поверх того же пути.

**Тема `owner: editor`** («пишем сами», см. шаг 4) — файла ещё нет,
только бриф. Frontmatter здесь действительно нужно построить с нуля:

1. Собрать frontmatter по шаблону `docs/content-rules.md` (title из
   дока или брифа, `draft: true` временно).
2. Сохранить в `src/content/blog/YYYY-MM-DD-<slug>.md`.
3. `/optimize-seo post <slug>` — не угадывать description/tags/
   categories/seo.keywords вручную, агент `seo-optimizer` для этого и
   существует.

Дальше — общее для обоих путей. **Снятие `draft` идёт только через
`release-article.mjs` — второго пути нет.** Раньше этот шаг сам ставил
`draft: false` и сам решал, блокировать ли по баллу — в обход
единственного канонического гейта, с другими правилами прохождения
(внешний аудит нашёл это как расхождение путей выпуска). Теперь:

4. `node scripts/factcheck/write-marker.mjs <slug>` — тело заменено
   (правки редактора из дока), маркер факчека привязан к старому хешу
   и без обновления не пройдёт ни один следующий шаг. Значимой
   фактической правки (цифра, дата, номер НПА) это не покрывает —
   такое требует полноценного `/factcheck <slug>`, не просто
   пересчёта хеша; решение, что это была за правка, за агентом.
5. `node scripts/cycle-state.mjs accept --slug <slug>` — это и есть
   зафиксированная человеческая приёмка: `release-article.mjs`
   проверяет именно этот статус в `editorial-cycle.json`, не
   придумывает свой.
6. `/analyze-article <slug>` — пересчитать: тело менялось, старая
   оценка не про эту версию текста.
7. `node scripts/release-article.mjs <slug>` — единственный гейт.
   Прогоняет НПА-аудит, битые ссылки, SEO P0, AI-маркеры, свежесть и
   балл оценки, факчек-хеш — сам, ничего из этого не нужно повторять
   вручную. Если балл < 70 и редактор явно решил принять статью
   несмотря на это — **не обходить, а** `node scripts/release-article.mjs
   <slug> --override-score "<конкретная причина редактора>"`: то же
   решение, но через тот же CLI, с причиной, записанной в
   `src/data/analyze/<slug>.json.releaseOverride` — а не молча. Любой
   другой блокер (битые ссылки, НПА, факчек-хеш) — не переопределять,
   чинить.
8. `node scripts/cycle-state.mjs release --slug <slug>` — статус темы
   в `editorial-cycle.json` до сих пор нигде не переводился в
   `released` после фактического выпуска: тема застревала в
   `accepted` навсегда, хотя файл уже был опубликован (колонка
   «Статус» из «## Шаг 5 — Синхронизировать статусы в таблицу» этого
   документа показывала редактору устаревшее значение). Только после
   успешного шага 7 выше.
9. Закоммитить: `content: <заголовок> (принято редактором)`.
10. `node scripts/social-state.mjs get <slug>` — если по статье не
   сделано ни одной площадки, добавить строку в отчёт: «рерайт под
   соцканалы не делали, запустить `/social-rewrite <slug>`». Именно
   напомнить, а не запустить: рерайт нужен не каждой статье, решение
   за человеком.

### 6б. Замечания в доке

```bash
node scripts/drive-sync.mjs comments --doc-id <id>
```

Отфильтровать по `seenComments` темы. Пусто — ничего не делать.

По каждому замечанию:

1. Прочитать `quotedFileContent.value` — к какому куску текста оно.
2. Внести правку **в док**, не в репозиторий: пока статья на вычитке,
   истина в доке. Править **точечно**, а не перезаливкой:

   ```bash
   node scripts/drive-sync.mjs replace-text --doc-id <id> \
     --find "<фрагмент как есть в доке>" --replace "<новый текст>"
   ```

   `make-doc` на этом шаге не использовать. Он удаляет тело дока целиком
   и пишет заново из markdown — вместе с ним исчезают правки, которые
   редактор или эксперт внесли руками после последнего экспорта, и
   съезжают якоря комментариев. Вопрос редакции 12.08.2026 был ровно об
   этом: «эксперт правит в файле, а бот через час перепишет — мы это
   увидим?». С `replace-text` — увидим: меняется только найденный
   фрагмент.

   Команда возвращает ненулевой код, если фрагмент не найден. Это не
   повод перезалить док: скорее всего текст уже поправили руками.
   Перечитать док (`export-doc`) и решать заново.
3. Ответить в треде и закрыть:

```bash
node scripts/drive-sync.mjs reply --doc-id <id> \
  --comment-id <cid> --text "Поправил: <что именно>" --resolve
```

4. Отметить разобранное:

```bash
node scripts/cycle-state.mjs seen-comments --slug <slug> --ids <cid1>,<cid2>
```

**Спорное замечание не выполнять вслепую.** Если редактор просит убрать
ссылку на НПА, которая нужна по редполитике, — внести бесспорное, а по
спорному ответить в треде вопросом с объяснением, чем это грозит, и
**не** закрывать тред.

### 6в. Заказано ТЗ дизайнеру

Тема пришла в `changes.designBrief` — редактор поставил «нужно ТЗ
дизайнеру» в колонке «Решение». Статус темы это значение не меняет:
статья как была на вычитке или принята, так и остаётся.

Выполнить `/design-brief <slug>` по процедуре
`.claude/commands/design-brief.md`: собрать исходные данные скриптом,
написать ТЗ, выложить доком в папку цикла, позвать дизайнера через
`notify`.

Два обязательных условия, иначе шаг пропускается с записью в отчёт:

- **Текст должен быть финальным.** ТЗ по черновику, который редактор
  ещё правит, — это иллюстрации к разделам, которых после правок не
  будет. Тема в статусе `review` без приёмки — сказать об этом в отчёте
  и не делать.
- **После выполнения вернуть в «Решение» прежнее значение** (`принято`
  или пусто) и вписать ссылку на ТЗ в колонку «Правка» строкой
  «ТЗ дизайнеру: <ссылка>». Оставите «нужно ТЗ дизайнеру» — следующий
  проход закажет то же самое второй раз.

## Шаг 7 — Недельная сводка (только в пятницу)

Проход в пятницу вечером — единственный, который пишет редактору, даже
если за неделю ничего не произошло. Молчание рутин рационально, но у
редактора нет способа отличить «всё спокойно» от «встало в понедельник»:
неделя без писем выглядит одинаково.

```bash
node scripts/weekly-digest.mjs --out /tmp/digest.md
node scripts/drive-sync.mjs make-doc --title "Сводка редакции — <дата>" \
  --md /tmp/digest.md --folder <drive.folderId>
node scripts/drive-sync.mjs notify --file-id <docId> --to <ящик редактора> \
  --message "Сводка за неделю: что ждёт вашего решения"
```

Док создаётся новый каждую неделю не для порядка в папке, а потому что
письмо Google шлёт только при первой выдаче доступа к файлу. Обновлять
один и тот же док — значит не отправить ни одного письма после первого.

Ящик редактора не задан — сводку всё равно собрать и вывести в отчёт
сессии: владелец передаст её сам.

## Правила

- Нет нового — выходить молча.
- Пока статья на вычитке, истина в Google Doc, а не в репозитории.
- Не согласовывать план за редактора и не ставить «принято» самому.
- Непонятную правку не угадывать — переспрашивать комментарием.
- Каждое изменение состояния коммитить и пушить сразу.
- Язык — только русский.
