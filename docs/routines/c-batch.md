Ты работаешь в репозитории burbonivanovich-oss/K_Editor — модуль-помощник для редактора и копирайтеров по тематике МСБ РФ (ТС ПИоТ, маркировка Честный знак, изменения в законодательстве). Инструкции проекта — CLAUDE.md, AGENTS.md и docs/, прочитай перед началом.

Это рутина C редакционного цикла. Выполни процедуру из .claude/commands/cycle-batch.md целиком. Полное описание цикла — docs/editorial-cycle.md.

Порядок работы:

1. git fetch origin main && git checkout main && git pull origin main.
2. ПРЕДОХРАНИТЕЛЬ, шаг 0: node scripts/cycle-state.mjs can-start-batch. НЕНУЛЕВОЙ КОД — СТОП: заверши работу молча, одной строкой с причиной, ничего не делая. Причины штатные: план ещё не одобрен, потолок очереди редактора, ботских тем нет, цикл idle или done. Эту проверку не обходить никогда и ни при каких обстоятельствах.
3. Код 0 — дальше по cycle-batch.md: next-batch (шаг 1), start-batch и sheet-sync (шаг 2), написание статей (шаг 3), выкладка в Google Docs (шаг 4), обновление таблицы и коммит (шаг 5), вызов редактора (шаг 6).

Автономность. Рутина работает без человека: спрашивать владельца можно
только тогда, когда правило не покрывает случай и цена ошибки высока.
Всё остальное решается по правилам и попадает в отчёт.

- Дубль с существующей статьёй — шаг 1б cycle-batch.md, правило есть.
  Проверять ДО ресёрча, а не посреди работы.
- Тема выглядит инструкцией («Актуализировать статью <ссылка>»,
  «Заголовок: …») — это задача, а не заголовок. Написать статью по
  инструкции, а заголовок взять из готового текста и вернуть в таблицу
  через cycle-state.mjs set-title.
- Незнакомый номер НПА — подтвердить по первоисточнику или убрать из
  текста. Не спрашивать.
- Не хватает доступа или падает сеть — повторить, потом написать в отчёт
  одной строкой и продолжить с остальными темами.

Остановка всего батча ради одного вопроса — худший исход: остальные темы
ждут ответа, которого может не быть до утра.

Развилка перед работой (шаг 1а): у каждой темы в выводе next-batch есть поле kind. kind: new (или поля нет) — новая статья, всё как ниже. kind: update — актуализация опубликованной статьи Маркета, идёт по .claude/commands/update-article.md: результат не статья, а документ правок в src/content/updates/ (цитата «Было», предлагаемая замена, источник, плюс раздел «что оставить как есть»). Ссылка на исходную статью, просьба редактора и опорные инструкции уже лежат в полях темы sourceUrl, brief, refUrls — прочитать их командой cycle-state.mjs get --slug <slug>, не пересказывать по памяти. Просьба редактора выполняется буквально, она сильнее шаблона. По задаче на актуализацию новая статья не пишется никогда, даже если так быстрее и оценка выше. Проверки другие: check-update-doc.mjs вместо check-seo и analyze-article. Батч смешанный — новые статьи и актуализации занимают очередь одинаково.

Как писать статьи (шаг 3, только kind: new):

- Каждая статья — полный пайплайн .claude/commands/create-article.md, все девять стадий со шлюзами. Не сокращать ради скорости.
- Категория с НПА (ts-piot, markirovka, zakonodatelstvo, egais, kkt) — research-specialist обязателен, все источники в брифе с verified: true. Номера ПП, приказов и ФЗ не выдумывать: проверяй по первоисточнику и сверяй с whitelist в src/data/factcheck/sources.json. Незнакомый номер — либо подтвердить и дописать в whitelist, либо убрать из текста.
- Обязательные артефакты по каждой статье: src/content/blog/YYYY-MM-DD-slug.md с draft: true, бриф на визуал src/data/visuals/<slug>.md, оценка src/data/analyze/<slug>.json, маркер .claude/factchecked/<slug>.
- Шлюзы прогонять скриптами, а не на глаз: node scripts/factcheck/audit-npa-references.mjs --strict, node scripts/check-seo.mjs, node scripts/check-ai-markers.mjs --save-profile (скор меньше 6), node scripts/audit/check-blog-links.mjs. Внутренние ссылки на статьи блога пишутся с датой в пути: /blog/YYYY-MM-DD-slug/ — так их проверяет check-blog-links.mjs.
- Промоблоки брать из кластера статьи по src/data/cpa-blocks.json. У кластера ts-piot своих блоков нет — тогда взять соседние (markirovka, kkt) и зафиксировать это в брифе на визуал.
- Сбой одной статьи не отменяет батч: не прошла шлюз после двух попыток — вернуть тему в planned, записать причину, остальные довести.
- Бюджет сессии: видно, что не дотянешь — доведи текущую статью, выложи готовое и завершись. Недописанные темы остаются planned.

Выкладка (шаг 4): frontmatter в Google Doc не выкладывать, в начало дока — врезка «Как вычитывать» по шаблону из cycle-batch.md. После make-doc привязать док к теме через cycle-state.mjs to-review. Если make-doc падает с fetch failed — это сетевой сбой, повтори вызов, скрипт удалит недоделанный док по имени сам.

Позвать редактора (шаг 6) — обязательный шаг, без него редактор о батче не узнает. По каждому свежесозданному доку: node scripts/drive-sync.mjs notify --file-id <docId> --to <ящик редактора> --message "Статья на вычитке: <заголовок>. Решение ставится в таблице плана, колонка «Решение»." Письмо шлёт Google при выдаче доступа — это единственный надёжный канал до почты. Уходит только при первой выдаче доступа к файлу, поэтому зовём по новым докам, а не по таблице плана: по ней доступ уже есть и notify вернёт код 2. Дополнительно — комментарий в таблице через drive-sync.mjs comment --mention, но письма по упоминанию Google не гарантирует, это не замена notify. Ящик редактора не задан или доступ к папке ещё не выдан — шаг пропускается, и это пишется в отчёт отдельной строкой: значит батч висит невидимым.

Правила: статьи остаются draft: true, флаг снимает только release-article.mjs. Темы «пишем сами» (owner: editor) не трогать. Язык — только русский.

Проверка перед завершением: node scripts/health-check.mjs — 0 fail (черновики в warn — норма); состояние и статьи закоммичены и запушены.

Отчёт — по форме из cycle-batch.md: сколько написано, ссылки на доки, позван ли редактор и как, что отложено и почему, очередь редактора N/6.
