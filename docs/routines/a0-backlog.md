Это вторая половина рутины A0 (недельный бэклог тем). Первая половина уже прошла: workflow .github/workflows/backlog.yml (крон, понедельник 06:00 UTC) собрал кандидатов и закоммитил src/data/topic-backlog.json на main — ты стартуешь через час после него, буфер на то, чтобы коммит успел уйти.

Эта Routine создана без GitHub-коннектора (mcp__github__* инструментов может не быть вообще — проверь это в начале). У тебя точно есть Bash и git. План рассчитан на то, что публикация (шаг 5) может не получиться автоматически — это не повод пропускать шаги 1-4.

Шаги:

1. git fetch origin main && git checkout main && git pull origin main — синхронизируй рабочую копию.

2. Прочитай src/data/topic-backlog.json. Если файла нет, или candidates пуст, или generatedAt не сегодняшняя и не вчерашняя дата (UTC) — значит backlog.yml не отработал или уже разобран. Ничего не делай, заверши коротким сообщением с причиной. Это обычное состояние, не ошибка.

2я. ПУБЛИКАЦИЯ — ДОПИСЫВАНИЕМ. Вкладка месячная, ресёрч еженедельный: новые темы идут строками ниже, а не заменяют прежние. Порядок: cycle-state add-candidates (отсекает дубли по слагу, назначает строки) → drive-sync append-topics → set-cells → set-row-dropdowns → verify-sheet. Новую вкладку (init-month) заводить только 1-го числа. После публикации — comment с упоминанием редактора: это сигнал «темы приехали», письма Google по API-комментариям не гарантирует.

2а. РАЗБОР РЕШЕНИЙ ПРОШЛОЙ НЕДЕЛИ — делается ДО работы с новыми кандидатами. Полный текст правил: .claude/commands/cycle-backlog.md, «Шаг 3 — Разобрать решения». Без этого шага решения редактора не читает никто: отказы не запоминаются и те же темы возвращаются каждую неделю.

- Найди таблицу прошлой недели (id — в сообщении прошлого прогона или в коммите «backlog: заголовки …»). Не нашёл — пропусти шаг и скажи об этом, не выдумывая id.
- Читай решения через мост в Actions: workflow ops.yml, задача backlog-decisions, вход sheet_id. Drive-секретов в сессии нет и быть не должно. JSON забирай из Summary прогона.
- «Одобрено» (в старых таблицах — «согласовано», pull-backlog приводит сам) → дописать тему в src/content/wiki/content-plan-2026.md, в таблицу своего кластера, пометка в колонке Blocker «backlog <дата>». Скрипта для переноса НЕТ, файл правится руками. После правки: node scripts/generate-editorial-plan.mjs.
- «Убрать» + «категорически не наше ядро» → suppressions.mjs add --reason core (90 дней). «Не тот угол» → --reason angle (30 дней) и предложить замену в этом же прогоне.
- «Нужен рерайт» → статья есть, но устарела. В заглушки НЕ писать и в контент-план новую тему НЕ добавлять: найти существующую статью, прогнать maintain-content-queue.mjs <slug> и дальше по maintain-content.md.
- Причина «пока рано — вернуть позже» или свой текст редактора → в заглушки не добавлять, тема вернётся сама.
- Проверить: suppressions.mjs list. Закоммитить и запушить.

2б. ИНФОПОВОДЫ — темы, которых нет в Wordstat. Полный текст: cycle-backlog.md, «Шаг 1в». Это обязательный шаг, а не опциональный: «с апреля 2026 продажи пива уходят в ЕГАИС автоматически» — тема с дедлайном и без частотности, и через спрос она не придёт никогда.

- Запусти /monitor-rss --window 30d --type news в этой же сессии. Окно 30 дней, а не 14: бэклог кормит месячный план.
- Отбери только то, у чего есть дата события. Нет даты — не инфоповод.
- Сложи в JSON массив: topic, cluster, source, eventDate (дд.мм.гггг), note. note — это готовое «Зачем сейчас»: что меняется, с какой даты, для кого. Номера НПА и цифры — только из источника, не выдумывать.
- Пересобери бэклог: node scripts/topics/generate-backlog.mjs --signals /tmp/signals.json. Инфоповоды отбираются до общего пула, в пределах квоты (6 из 40) — сортировка по спросу их бы похоронила.
- Сигналов нет — нормальный исход, квота не расходуется. Пустой список лучше выдуманного события.

3. Если кандидаты свежие: перепиши поле topic каждого кандидата в заголовок статьи по правилам cycle-backlog.md, «Шаг 1а». targetKeyword НЕ трогай. Опирайся только на why, cluster, normHint, type. 50-80 символов, без кликбейта и вопросительной формы в начале.

3а. Перепиши поле why — «Зачем сейчас» — по правилам cycle-backlog.md, «Шаг 1б». Скрипт собирает его шаблоном, и у всех свежих фраз он одинаковый; редактор перестаёт читать колонку, ради которой открывает таблицу. Опирайся на спрос, покрытие кластера, normHint, тип интента, ценность для перелинковки и дедуп с Маркетом. Одинаковых формулировок быть не должно. Фактов, которых нет в кандидате, не примысливать.

4. Сохрани переписанный JSON обратно, закоммить «backlog: заголовки <дата>», запушь в main. Делается всегда, независимо от шага 5.

5. Опубликуй таблицу через workflow backlog-publish.yml (mcp__github__actions_run_trigger, либо curl с токеном из окружения, либо попроси владельца запустить вручную).

Жёсткие ограничения:
- Никогда не трогай targetKeyword, decision, author, declineReason у кандидатов.
- Никогда не выдумывай факты (нормы, даты, суммы) сверх того, что уже в why/normHint или в источнике инфоповода.
- Заголовки и обоснования инфоповодов не переписывай вслепую: note от мониторинга уже содержит суть, его надо сохранить, а не заменить шаблоном.
- Никогда не вызывай drive-sync.mjs и не используй секреты GOOGLE_DOCS_KEY/GSC_* в этой сессии — только через ops.yml и backlog-publish.yml.
- Не ставь решения за редактора.
- Шаг 4 выполняется всегда.
- Язык — только русский.

В конце — короткое сообщение: что разобрано по решениям прошлой недели, сколько новых тем, каким путём опубликовано, ссылка на таблицу.
